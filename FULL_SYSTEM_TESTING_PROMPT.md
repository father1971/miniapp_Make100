> [!IMPORTANT]
> Этот промпт предназначен для агента/разработчика, который проводит комплексное тестирование системы Make 100. Необходимо протестировать **все взаимодействия** между фронтендом, бэкендом и базой данных — на корректность, производительность и отказоустойчивость.

## Контекст проекта

**Make 100** — Telegram Mini App + веб-версия. Математическая игра: из 6 цифр номерного знака/билета нужно составить выражение = 100.

- **Фронтенд:** React + TypeScript + Vite (размещён на GitHub Pages / Cloudflare Pages)
- **Бэкенд:** Cloudflare Worker (`make100-backend.rotanovav.workers.dev`)
- **БД:** Cloudflare KV (пулы изображений) + D1 / Workers KV (статистика пользователей)
- **Тест-окружение:** `https://father1971.github.io/miniapp_Make100/` (ветка `main`, тестовый бот `@Test_Make100_bot`)
- **Prod-окружение:** `https://make100-3ow.pages.dev` (ветка `prod`, бот `@Make_100_Bot`)
- **Существующие E2E-тесты:** `e2e/scenarios/` (Playwright)

## БЛОК 1: Аутентификация и авторизация

### 1.1 Telegram WebApp Auth (инициализация)

**Тест:** Фронтенд корректно читает `window.Telegram.WebApp.initData` и передаёт в заголовке `Authorization: Bearer <initData>`.

- [ ] `GET /api/user` с валидным `initData` → `200 OK`, возвращает объект пользователя с полями `id, firstName, coins, hintsCount, solvedCount, ...`
- [ ] `GET /api/user` с невалидным/подделанным `initData` → `401 Unauthorized`
- [ ] `GET /api/user` без заголовка Authorization → `401` или `403`
- [ ] Бэкенд правильно верифицирует подпись Telegram (HMAC-SHA256)
- [ ] **Производительность:** Время ответа `/api/user` при холодном старте Workers ≤ 500 мс, при теплом ≤ 150 мс

### 1.2 Email OTP Auth (веб-версия)

- [ ] `POST /api/auth/email/send-code` с валидным email → `200`, поля `success: true, otpSession: string`
- [ ] `POST /api/auth/email/send-code` с некорректным email (без `@`) → `400`, `error: 'invalid_email'` или подобное
- [ ] `POST /api/auth/email/send-code` повторная отправка < 60 сек → `429 Too Many Requests` (rate-limiting)
- [ ] `POST /api/auth/email/verify-code` с верным кодом → `200`, поля `success: true, token: string, user: {...}`
- [ ] `POST /api/auth/email/verify-code` с неверным кодом → `400`, `error: 'invalid_or_expired_code'`
- [ ] `POST /api/auth/email/verify-code` через 10 мин (OTP истёк) → `400`, `error: 'expired'`
- [ ] Фронтенд после успешного верификации сохраняет `token` в `localStorage['make100_web_auth_token']`
- [ ] Последующие запросы идут с `Authorization: Bearer <token>`

### 1.3 Telegram Widget Auth (web-версия)

- [ ] `POST /api/auth/telegram-widget` с валидными `widgetData` от Telegram Login Widget → `200`, `{success: true, token, user}`
- [ ] `POST /api/auth/telegram-widget` с устаревшей подписью (> 86400 сек) → `401`
- [ ] Фронтенд сохраняет `token` и `user` в localStorage

### 1.4 Ban Check

- [ ] `GET /api/user` для забаненного пользователя → `403`, тело `{error: "banned"}`
- [ ] Фронтенд при получении `403 + error=banned` устанавливает `isBanned=true`, отображает экран блокировки
- [ ] Забаненный пользователь не может делать другие запросы к API

## БЛОК 2: Пользовательские данные (CRUD)

### 2.1 GET /api/user — Загрузка профиля

**Формат ответа (обязательные поля):**
```json
{
  "id": 12345678,
  "firstName": "string",
  "lastName": "string",
  "username": "string",
  "avatarUrl": "string | null",
  "score": 0,
  "solvedCount": 0,
  "skippedCount": 0,
  "bestTimeMs": null,
  "minCharacters": null,
  "totalTimeMs": 0,
  "totalCharacters": 0,
  "coins": 100,
  "hintsCount": 3,
  "referredBy": null,
  "referralCount": 0,
  "gamesStarted": 0,
  "createdAt": 1700000000000,
  "settings": { "language": "ru", "gameMode": "ticket", ... },
  "modeStats": { "tickets": {...}, "car": {...} }
}
```

- [ ] **Новый пользователь (первый вход):** При GET возвращается `404` → фронтенд делает `POST /api/user` для регистрации → новый пользователь получает `coins: 100, hintsCount: 3`
- [ ] **Новый пользователь с реферером (`?referredBy=<id>`):** `coins: 250` (REFERRAL_WELCOME_COINS), `referredBy = <id>`
- [ ] **Существующий пользователь:** Данные совпадают с тем, что записано в БД
- [ ] `GET /api/user?userId=<id>` — просмотр чужого профиля без авторизованных данных (публичные поля)
- [ ] **Производительность:** ≤ 200 мс для теплого Workers

### 2.2 POST /api/user — Сохранение статистики/настроек

- [ ] Обновление `settings` (язык, тема, режим, звук, вибрация) → `200`, `{success: true, stats: {...}}`
- [ ] Данные персистируются: повторный `GET /api/user` возвращает обновлённые настройки
- [ ] Нельзя напрямую обнулить `coins` / `score` через POST (сервер игнорирует или валидирует)
- [ ] Фронтенд вызывает `saveUserStats()` при изменении: языка, темы, режима, звука, вибрации
- [ ] Фронтенд НЕ вызывает `saveUserStats()` до завершения загрузки статистики (`isStatsLoadedRef.current = false` → автосохранение заблокировано)

## БЛОК 3: Игровые эндпоинты

### 3.1 POST /api/game/solve — Правильное решение

**Payload:**
```json
{
  "formula": "1+2*3-4+5*6",
  "digits": ["1","2","3","4","5","6"],
  "elapsedTimeMs": 15320,
  "gameMode": "ticket"
}
```

**Ожидаемый ответ:**
```json
{
  "success": true,
  "score": 110,
  "coins": 160,
  "solvedCount": 6,
  "skippedCount": 2,
  "modeStats": { "tickets": { "solvedCount": 6, "bestTimeMs": 12300, "minCharacters": 5 } }
}
```

- [ ] Формула корректно оценивается = 100 → `success: true`
- [ ] Счёт (`score`) увеличивается на сервере
- [ ] Монеты (`coins`) увеличиваются на +10 за решение
- [ ] Обновляется `solvedCount` (+1 для текущего gameMode)
- [ ] Обновляется `bestTimeMs`: если время лучше — устанавливается новый рекорд
- [ ] Обновляется `minCharacters`: если формула короче — фиксируется
- [ ] Обновляются `modeStats.tickets` или `modeStats.car` в зависимости от `gameMode`
- [ ] Фронтенд после ответа обновляет локальный стейт (`stats.coins`, `stats.score`, etc.)
- [ ] Формула с неправильным результатом (≠100) → `400`, `{success: false, error: "wrong_answer"}`
- [ ] Дублирующий запрос (повторная отправка той же формулы в течение 5 сек) → идемпотентность или `409`
- [ ] **Производительность:** ≤ 300 мс

### 3.2 POST /api/game/skip — Пропуск раунда

**Payload:** `{ "gameMode": "ticket" }`

- [ ] → `200`, `{success: true, skippedCount: N, ...}`
- [ ] `skippedCount` увеличивается на +1
- [ ] `score` НЕ изменяется (или уменьшается по правилам — проверить реальную логику)
- [ ] Монеты НЕ начисляются за пропуск
- [ ] Фронтенд после ответа инициирует новый раунд `initGame()`
- [ ] Guest-режим (без авторизации): skip работает локально, без запроса к серверу — проверить что запрос НЕ отправляется

## БЛОК 4: Система подсказок

### 4.1 POST /api/user/use-hint — Использование подсказки

- [ ] При `hintsCount > 0` → `200`, `{success: true, hintsCount: N-1, coins: ...}`
- [ ] При `hintsCount = 0` → `400`, `{success: false, error: "no_hints_remaining"}`
- [ ] Фронтенд оптимистично уменьшает счётчик **до** запроса (optimistic update)
- [ ] При ошибке сервера — фронтенд восстанавливает предыдущее значение `hintsCount`
- [ ] `isSubmittingHint` блокирует повторные клики во время запроса

### 4.2 POST /api/user/buy-hint — Покупка подсказки

**Стоимость: 20 монет (HINT_COST_COINS)**

- [ ] При `coins >= 20` → `200`, `{success: true, hintsCount: +1, coins: coins-20}`
- [ ] При `coins < 20` → `400`, `{success: false, error: "insufficient_coins"}`
- [ ] После покупки: `hintsCount` увеличивается, `coins` уменьшается на 20
- [ ] Данные обновляются в БД
- [ ] Фронтенд обновляет `stats.hintsCount` и `stats.coins` из ответа

## БЛОК 9: Сетевые сценарии (Fault Tolerance)

### 9.1 Таймауты и retry

- [ ] При timeout сервера (> 15 сек): `AbortController` срабатывает, запрос отменяется, функция возвращает `null`
- [ ] GET-запросы автоматически повторяются до 2 раз (retries = 2)
- [ ] POST-запросы НЕ повторяются (retries = 0 для не-идемпотентных)
- [ ] При 500-ошибке сервера на GET: exponential backoff (500ms, 1000ms, ...)
- [ ] При 4xx на POST: тело ошибки парсится и возвращается клиенту

### 9.2 Офлайн-режим / деградация

- [ ] При отсутствии сети: фронтенд использует `localStorage` кеш для статистики (`stats_<userId>`)
- [ ] При отсутствии сети: пул изображений берётся из `localStorage['make100_kv_images']`
- [ ] При ответе `null` от API: фронтенд не крашится (ErrorBoundary перехватывает)
- [ ] Guest-пользователь (без auth): solve/skip работают локально без обращения к серверу

### 9.3 Параллельные запросы / Race Conditions

- [ ] Двойной клик на "Решить" → только один запрос отправляется (`isPending` блокирует)
- [ ] Смена раунда во время pending solve → корректная отмена / игнорирование устаревшего ответа
- [ ] Параллельная загрузка изображений + загрузка статистики → не блокируют друг друга

## БЛОК 11: Математический движок (mathEngine)

> [!NOTE]
> Это клиентская логика, но критична для корректности игры. Тестируется изолированно.

### 11.1 calculateResult() — Корректность вычислений

- [ ] `1+2+3+4+5*6` при digits=`[1,2,3,4,5,6]` → `51`? (проверить приоритет операций)
- [ ] `(1+2)*3+4*5+6` → `6*3+20+6 = ...` (проверить скобки)
- [ ] Деление с нецелым результатом (не оканчивающаяся дробь) → `NaN` (результат должен быть целым или оканчивающейся дробью)
- [ ] Деление на 0 → `NaN`
- [ ] Пустые скобки `()` → `NaN`
- [ ] Число с ведущим нулём `025` → `NaN`
- [ ] `calculateResult(['1','0','0'], ['','','',''])` → `100` ✓

### 11.2 findSolution() — Поиск решения

- [ ] Для `['1','0','0']` → решение `['','','','']` (100 = 100)
- [ ] Для цифр, у которых есть решение → возвращает минимально короткую формулу
- [ ] Для цифр, у которых НЕТ решения → возвращает `null`
- [ ] Время работы `findSolution(['9','9','9','9','9','9'])` ≤ 2000 мс (сложный случай)

### 11.3 isOpAllowed() — Smart Button Guard

- [ ] Слот 0: допустимы `(` и `-`, запрещены `+`, `*`, `/`, `)`, `,`
- [ ] Слот 6 (последний): допустима только `)` при наличии незакрытых скобок
- [ ] Промежуточный пустой слот: `(` запрещена до нажатия оператора
- [ ] Запятая `,` запрещена если в числовом блоке уже есть запятая
- [ ] Лимит слота 5 символов
- [ ] `Backspace` доступен только если слот не пустой

## БЛОК 13: Безопасность

- [ ] SQL injection в полях `email`, `name` → сервер не падает, данные sanitized
- [ ] XSS в полях обратной связи → данные не исполняются
- [ ] CORS: только разрешённые домены могут делать запросы
- [ ] Нельзя передать чужой `userId` и получить чужие данные (проверка через `initData`)
- [ ] Нельзя напрямую задать `coins = 999999` через POST /api/user
- [ ] Rate limiting на auth-эндпоинты (email OTP): не более 5 запросов в час с одного email
- [ ] JWT токены (web auth) имеют срок действия и не принимаются после истечения

## БЛОК 14: Интеграционные сценарии (End-to-End flows)

### Сценарий A: Полный жизненный цикл Telegram-пользователя
1. Пользователь открывает Mini App по реферальной ссылке `?start=<referrerId>`
2. Фронтенд читает `initData` → отправляет `GET /api/user?referredBy=<referrerId>`
3. Новый пользователь → `POST /api/user` → `coins = 250, hintsCount = 3`
4. Трекинг реферального визита → `POST /api/referrals/visit`
5. Игра: решает 3 задачи → 3× `POST /api/game/solve` → `coins += 30, solvedCount = 3`
6. Пропускает 1 задачу → `POST /api/game/skip` → `skippedCount = 1`
7. Использует подсказку → `POST /api/user/use-hint` → `hintsCount = 2`
8. Покупает подсказку → `POST /api/user/buy-hint` → `coins -= 20, hintsCount = 3`
9. Открывает лидерборд → `GET /api/leaderboard?userId=<id>` → видит свою позицию
10. Настройки: меняет язык на English → `POST /api/user` с новыми settings
11. Перезагружает страницу → все данные восстанавливаются с сервера

**Проверить:** последовательность, корректность данных на каждом шаге, отсутствие рассинхрона между локальным стейтом и БД

### Сценарий B: Гость → Email Auth → Сохранение прогресса
1. Гость играет 5 раундов (локально, без сервера)
2. Регистрируется через Email OTP
3. Локальный прогресс мержится с серверным профилем (или теряется — задокументировать поведение)

### Сценарий C: Переключение режимов Ticket ↔ Car
1. Пользователь играет в режиме Ticket (несколько решений)
2. Переключает на режим Car
3. `modeStats.tickets` и `modeStats.car` обновляются независимо
4. `bestTimeMs` и `minCharacters` считаются отдельно для каждого режима
